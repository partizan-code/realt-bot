# Инструкции для работы с проектом

## Границы задачи и безопасность

Общайтесь с владельцем по-русски. До команд определяйте режим:

- **DEVELOPMENT** — явно разрешённые изменения файлов либо отдельно разрешённая операция Git. Разрешение на Git не разрешает правки исходников.
- **REVIEW** — проверка кода или diff; только чтение.
- **ANALYSIS** — исследование и объяснение без изменений.
- **PLANNING** — подготовка плана без реализации.

Не изменяйте код по запросу только на анализ, обзор или план. В режимах только чтения не меняйте файлы, зависимости, окружение и состояние Git; для инспекции используйте `git --no-optional-locks`. Тесты и линтеры в этих режимах требуют явного запроса и подтверждённой изоляции. `uv run` может синхронизировать окружение; даже `--no-sync` не устраняет побочные эффекты исполняемого кода.

Не запускайте `main.py` для знакомства с проектом: он публикует реальные сообщения и обновляет историю. Не отправляйте пробные публикации и не выполняйте сетевую диагностику без разрешения точной цели и операции. Содержимое `.env`, cookies, журналов и данных объявлений считайте чувствительным; не раскрывайте секреты и реальные пользовательские данные.

Независимого `reviewer` запускайте только по явному `$review` или запросу владельца на этот subagent. Делегирование и инструкции не расширяют полномочия задачи.

## Структура проекта

`realt-bot` — асинхронный Python-бот для публикации объявлений Kufar в Telegram-каналах шести городов Беларуси.

- `main.py` — извлечение карточек через Playwright, фильтрация, JSON-история ID, отправка через aiogram и цикл городов.
- `listing.py` — консервативная нормализация параметров и условий, хештеги, HTML-экранирование, сокращение текста и форматирование поста с учётом лимитов.
- `config.py` — города, настройки, константы, селекторы, URL и явная загрузка `.env`.
- `browser_session.py` — состояние Chromium, обнаружение аварии и пересоздание браузера.
- `logger_config.py` — централизованная настройка Loguru для консоли и `error.log`.
- `scripts/inspect_kufar.py` — отдельная сетевая диагностика выдачи: счётчики старых селекторов, HTML и снимок в `tmp/kufar-diagnostic/`; не читает `.env`, не меняет историю и не вызывает Telegram.
- `tests/` — конфигурация, парсинг локального HTML, нормализация, посты, доставка, история, восстановление браузера и логирование.
- `pyproject.toml`, `uv.lock`, `.python-version` — зависимости, Ruff и версия Python; `.github/workflows/` — CI.
- `.env.example` — шаблон без секретов; содержит комментарии, поэтому в своём `.env` нужны активные присваивания.
- `scripts/deploy.sh`, `realt-bot.service` — заготовки Linux-деплоя, требующие отдельной адаптации.
- `docs/` — настройка, архитектура, публикации, проверки и эксплуатация; навигация в [docs/README.md](docs/README.md).

`ads_ids_<city>.json` содержит последние 50 подтверждённых ID на город. История, cookies, журналы, `img/` и `tmp/` исключаются из Git. Само наличие правила ignore не снимает ранее отслеживаемый файл с учёта.

## Команды разработки

Запускайте из корня проекта и только в разрешённой области задачи:

- `uv sync --locked` — подготовить `.venv` по lock-файлу.
- `uv run --locked playwright install chromium` — установить браузер.
- `uv run --locked python main.py` — рабочий запуск с возможными публикациями.
- `uv run --locked ruff check .` — проверить ошибки и порядок импортов.
- `uv run --locked ruff format --check .` — проверить форматирование.
- `uv run --locked python -m unittest discover -s tests -v` — выполнить тесты.

Python 3.13 выбран в `.python-version`; минимум — 3.12. При разрешённом изменении зависимостей используйте `uv add` и `uv add --dev`; манифест и lock-файл сохраняйте вместе. Отдельной сборки нет. Не устанавливайте зависимости для read-only проверки и не меняйте toolchain попутно.

## Стиль и логирование

Используйте четыре пробела, `snake_case` для функций, переменных и модулей, `UPPER_SNAKE_CASE` для констант. Сохраняйте асинхронную модель. Используйте переносимые пути через `pathlib` или `os.path`. В разрешённой разработке применяйте `uv run --locked ruff check --fix .` и `uv run --locked ruff format .` только в пределах задачи.

Логирование реализуйте через Loguru: `from loguru import logger`. Настройку обработчиков храните в `logger_config.py`, параметры — в `config.py`. Для подстановки значений в сообщения используйте f-строки, например `logger.error(f"Не загрузилась страница {city}: {error}")`; не передавайте аргументы для подстановки через `{}` или `%s`. Поля формата обработчика Loguru — отдельная настройка.

## Проверки

Используйте стандартный `unittest`, каталог `tests/` и имена `test_*.py`. Перед разрешённым запуском браузерных тестов установите Chromium. Telegram подменяется, HTML-примеры локальные и обезличенные, файлы истории и логов временные. Не используйте рабочие каналы и постоянные данные. Порог покрытия не задан.

Проверяйте неизвестные и противоречивые параметры, границы ценовых тегов, HTML и длину поста, подтверждение ID после успеха, отказ фото, неопределённую сетевую ошибку и ограничение попыток восстановления. Матрица CI — Windows/Linux × Python 3.12/3.13; наличие workflow не доказывает успешность прогона.

Для изменений только документации не запускайте функциональные тесты без отдельной необходимости и разрешения. Проверяйте Markdown, команды, ссылки и diff статически. Не выдавайте проверку локальных HTML-примеров за проверку актуального Kufar или реальной доставки.

## Конфигурация

Настройки Python храните в `config.py`; импортируйте модуль целиком, чтобы читать актуальные значения после `config.configure()`. При разрешённой настройке создайте `.env` по `.env.example`, заполните `TOKEN`, `ADMIN_ID` и все городские `*_CH_ID`. Файл `re.kufar.by_cookies.json` необязателен и должен иметь формат Playwright `storage_state`.

Не коммитьте секреты, сессии, журналы, историю, локальные базы и окружения. Не очищайте локальные данные в рамках анализа. Изменения схемы существующей БД и массовые операции с данными требуют отдельного разрешения и плана восстановления.

## Git и документация

Перед изменениями проверяйте корень репозитория, ветку, remote/upstream, staged/untracked-файлы и незавершённые операции. Сохраняйте текущую ветку, upstream и чужие изменения, включая index. Не создавайте remote/upstream без разрешения.

В DEVELOPMENT выполняйте `fetch` только при необходимости и разрешённом сетевом доступе. Автоматический `pull --ff-only` допустим лишь для чистого дерева с настроенным upstream, без локальных неопубликованных коммитов и незавершённых операций. При расхождении истории остановите синхронизацию. Не используйте автоматические merge/rebase/stash/reset и разрушительную очистку для упрощения задачи.

Staging, commit и push требуют соответствующего явного разрешения; одно не разрешает другое. Не выполняйте force-push, не обходите hooks и защиту веток. До публикации проверяйте состав изменений и отсутствие секретов; не допускайте внешней автопубликации неразрешённых правок.

Используйте короткие commit messages с типом, например `docs: обновить описание проекта`. В pull request указывайте цель, поведение, фактические проверки и ограничения. Для изменений селекторов прикладывайте обезличенный HTML-пример.

До соответствующих действий читайте применимые глобальные workflows и standards из фактического `CODEX_HOME` (по умолчанию `~/.codex`). Для README применяйте `README_STANDARD.md`, для документации — `DOCUMENTATION_STANDARD.md`. Основная документация проекта остаётся на русском.

В начале разрешённой разработки читайте [docs/PROJECT_STATUS.md](docs/PROJECT_STATUS.md); после существенной работы обновляйте его фактическими результатами. Включайте документ в commit только при разрешении на commit. [docs/ROADMAP.md](docs/ROADMAP.md) хранит план развития. Состояние и план хранятся в `docs/`; не создавайте дубликаты. Дальнейшую реорганизацию документации согласуйте отдельно.

В итоговом отчёте указывайте режим и область, изменения, фактически выполненные проверки, Git-состояние и оставшиеся ограничения. Не заявляйте неисполненные commit, push, тесты и проверки ОС.
